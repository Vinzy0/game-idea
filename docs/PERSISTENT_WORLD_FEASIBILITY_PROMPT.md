# Feasibility Review Prompt — Persistent AI World With an Always-On Board

Copy everything below into a strong reasoning model. I want an honest feasibility review, not implementation yet.

---

I am building a local-first, single-player AI-DM tactical RPG in TypeScript, React, Phaser, and Vite. The existing prototype already has:

- a deterministic, framework-neutral tactical engine;
- a data-defined ability system;
- player and enemy turns;
- movement, pathfinding, HP, downing, and action resources;
- simple deterministic enemy AI;
- walls, doors, desks, lockers, barrels, hazards, destructible objects, and difficult terrain;
- a Phaser board renderer and React HUD;
- a provider-neutral AI interface for narrative, structured output, and dialogue;
- narrative chat, approval of major irreversible events, bounded context, and a deterministic offline Demo provider;
- versioned local story persistence.

The current demo map is 12×8, but I want to pivot the product in this direction:

## Product idea

The 2D play area should always be visible. It should not appear only when combat begins.

The game always has one active 32×32 tile scene. A scene represents one room-scale or local area, such as a classroom, laboratory, house floor, hallway section, courtyard, street section, or forest clearing. The player explores, talks, inspects, interacts, and fights on this same board.

Outside combat, movement is free and click-to-move. Inside combat, the same board switches to strict turn-based movement and actions. Combat ending returns the same board to exploration; there is no separate combat screen.

The wider world is generated by the AI as needed rather than built in advance. The AI may invent locations, characters, factions, relationships, objectives, and events. These receive stable IDs and are saved as canon. When the player travels through an exit:

- an already-created destination reloads exactly as saved;
- an unknown destination is generated once, validated, assigned permanent IDs, saved, and then loaded;
- destroyed objects, opened doors, injuries, downed characters, relationships, and important events persist when the player returns.

The AI does not generate arbitrary code or control mechanics directly. It returns structured proposals. Deterministic code validates them, assigns IDs, compiles approved scene templates/catalog pieces into engine configuration, and commits changes atomically. Mechanical truth such as HP, positions, valid movement, action costs, object state, and battle outcomes remains owned by the engine.

For the first version, every scene is exactly 32×32. Map generation is template-guided rather than raw tile-by-tile generation. The AI chooses from approved room archetypes and catalog pieces, supplies narrative content and occupants, and the deterministic compiler creates a valid board. The initial visual/map theme is a school. Later versions can add more themes and templates.

Persistence is local-first. The browser version will keep one versioned active world save in IndexedDB, with JSON export/import. A later Electron version can use real save folders and Markdown memory files. Structured JSON is authoritative for mechanics and canon; AI-facing Markdown summaries are derived memory, not mechanical truth.

The intended loop is:

```text
Create character and world
→ Generate and save initial 32×32 scene
→ Explore on the board
→ Talk and act through the AI DM
→ Travel to saved or newly generated scenes
→ Conflict starts on the same board
→ Turn-based combat
→ Structured result is committed
→ AI continues the story
→ World and scene changes remain permanent
```

5. What are the largest architecture risks involving state ownership, AI inconsistency, persistence, map validation, and transitions between exploration and combat?

7. Is the project scoped reasonably for an iterative vertical slice, or is the first slice still too large?
8. What should the smallest convincing version contain?
9. What should explicitly be postponed?
